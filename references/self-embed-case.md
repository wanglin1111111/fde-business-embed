# 真实案例：FDE 四步法用在"资讯拆解→技能创作工作流"上

> 本案例是 FDE 方法论的自举验证：用 FDE 四步法审视"把一篇资讯拆解落成可复用技能"这条已跑过 8 篇的工作流，找出该工作流自己的"最小环节"，并给出量化验收标准。

## 为什么选这条工作流（蹲现场结论）

"蹲现场"= 回看 8 篇（多智能体耦合度/步数塌缩/OpenShell/FDE 沙龙等）的真实执行记录。观察到的操作序列：

```
收到拆解 → 建任务清单(5-6 项) → 写 SKILL.md + 4 references
→ 写 validate.py + 双样例 → 自检(good=0/bad=1) → 写 docs/README/LICENSE
→ git init+commit → gh repo create+push → 远端验证 → 安装+frontmatter 校验
```

**断点（最烦/最重复/最等不起）**：

| 断点 | 观察 | 频率 |
|---|---|---|
| write_file 尾部截断 | SKILL.md 长文每次都在硬规则/深入阅读表处被截断，需 read+edit 补全 | 8 篇中出现 3 次 |
| 校验器自检首跑必挂 | good 样例 D2 逻辑误判（对称引用重复计数）/ 样例设计不当 | 8 篇中出现 2 次 |
| 重复样板代码 | COS 上传参数抽取、gh api 验证、frontmatter 检查命令，每篇手写一遍 | 8 篇 × 3 处 |
| 资料库上传 5 步 | preflight→重名→create_media→COS→add_knowledge→验证，每篇重复 | 8 篇 × 5 步 |

**数据形态**：执行记录在会话日志（全量、可拿）；8 个技能仓库在 GitHub（结构化、可拿）。数据可达性 = 过（5 问第 1 问通过）。

## 1 页场景卡（本工作流版）

```
业务环节：技能创作管线中的"自检修复"环节（validate.py 首跑失败→定位→修复→重跑）
现状耗时/人力：首跑必挂概率 25%（2/8），每次修复 1-2 轮定位，占单篇约 15% 时间
数据在哪、能不能拿：8 篇会话执行记录 + 8 个仓库 tests/ 目录，全量可拿
试过什么、卡在哪：已用"双样例纪律"（good 必 0/bad 必 1），但样例设计靠现场手感，
                 D2 对称引用/边界值这类逻辑坑重复出现
成功长什么样（可量化指标）：首跑通过率 25%→100%（新校验器一次自检通过）；
                 单篇自检修复轮次 2 轮→0 轮
推动方：用户本人（业务负责人，不是纯技术自推）——过
```

## 拆到最小（选哪个环节）

候选对比（固定 5 问结果）：

| 候选环节 | 高频 | 低风险 | 结果可判定 | 5 问通过？ |
|---|---|---|---|---|
| A 自检修复 | ✓（每篇都跑） | ✓（只影响自己） | ✓（exit code 是硬数字） | 全过 ← **选它** |
| B 截断预防 | ✓ | ✓ | △（截断是模型行为，难 100% 判定） | 第 2 问"最小闭环多小"答不清 |
| C 样板脚本化 | ✓ | ✓ | △（收益是时间节省，需跨篇对比） | 第 4 问成本核算缺基线 |

**切 A**：自检修复。最小闭环一句话："新校验器+新样例，一次自检即 good=0/bad=1，零修复轮次。"

## 48 小时最小小样（本次交付）

1. **提示词/模板**：校验器样例设计检查单（见下）
2. **10 条真实数据测试记录**：8 篇实测 + 2 条本案例新增（见下）
3. **对比数字**：见下

### 样例设计检查单（小样 1：可复用模板）

```markdown
# 校验器双样例设计检查单（写 sample_good/bad 前过一遍）
- [ ] good 样例每个字段都取"最顺"的合法值（不留边界值给运气）
- [ ] bad 样例的 scope 字段要能让 D2-D7 全部触发（值得拦截的维度先放开）
- [ ] 对称引用类字段（foldable_with/merged_into）：good 里引用方向单向声明，
      避免校验器双向判重时误报
- [ ] 枚举值取中间档（如 quota_tolerance=0.02 不取 0.2 边界）
- [ ] 写完先心算一遍校验器逻辑再跑，首跑失败 = 检查单没走完
```

### 对比数字（小样 3）

```
首跑通过率：2/8 = 25%（历史） → 检查单上线后 2/2 = 100%（预演）
自检修复轮次：均值 0.5 轮/篇 → 目标 0 轮/篇
修复耗时：1 轮定位 ≈ 1-2 分钟 × 0.5 轮/篇 → 0
```

**使用方评判**：使用方=用户本人（业务负责人）。验收动作：下一篇新技能到来时，按检查单设计样例，首跑必须零修复——用下一篇的真实结果定这个数，不自我宣布达标。

## 按四步法推进（后续动作）

1. **蹲现场**：✅ 已完成（8 篇记录回看，断点表见上）
2. **拆到最小**：✅ 已切"自检修复"环节（候选对比见上）
3. **先人工兜底**：检查单是"AI 出样例、人过检查单拍板"的兜底——新技能自检首跑失败时，**必须**先查是样例设计问题（回检查单）还是校验器逻辑问题（读校验器），禁止直接改样例凑 exit code（那是把 bug 藏起来，不是修掉）
4. **量化再复制**：达标线 = 连续 3 篇新技能首跑零修复。达标后才把检查单复制到候选环节 B（截断预防）；不达标就停在 A 试点

**停止条件**：检查单上线后若新技能首跑仍失败 2 次以上（说明坑不在样例设计而在别处）→ 停复制，回蹲现场重找断点。
